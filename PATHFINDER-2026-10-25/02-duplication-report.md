# 重复、分歧与可简化点

以下均基于当前源码静态检查。涉及表现的风险尚未在本轮浏览器中重现，不将其描述成已经实测的故障。

## 1. 三种预览与游戏不使用同一条动画处理路径

- 游戏轨道过滤：`src/main.js:779`；动作编辑器独立过滤：`src/motion-editor.js:1531`；模型编辑器另有过滤：`src/model-editor.js:1621`。
- 游戏 Root 采样／转换：`src/main.js:431,576`；动作编辑器独立采样／转换：`src/motion-editor.js:1680,1437`。
- 招式编辑器加载原片段 `src/move-manager.js:154`，`applyPose` 在 `:245` 固定外层位置并直接采样 mixer；动作编辑器 `src/motion-editor.js:522` 则积分世界位移并分开处理 Root 姿态。
- 价值：这是“编辑器调好，进游戏还要重调”的明确结构风险，应优先统一数学语义。
- 合理差异：编辑器任意时间拖拽、游戏增量推进和碰撞阻挡必须保留；不能靠复制整个游戏帧循环解决。
- 默认合并也有差异：`src/main.js:780` 只在整个动作条目缺失时使用默认对象，`src/motion-editor.js:1532` 与 `src/model-editor.js:1622` 则补齐部分条目的字段。提取前须记录旧配置行为，不能把整理代码变成静默改参数。

## 2. 最终循环和速度语义不够集中

- `src/main.js:732` 强制攻击单次播放，即使动作配置的 loop 为 true。
- `src/move-manager.js:236` 总循环，`:243` 按 1 倍推进；`src/motion-editor.js:1196,1359` 使用独立预览循环。
- `src/motion-editor.js:1374` 将目标速度换算结果限制为 0.5–3；游戏 `src/main.js:2821` 的移动路径允许限制为 0–3。
- 独立预览循环是合理功能，问题是不能让作者误认成保存后游戏的实际行为。
- 建议统一有效配置解析和速度换算，明确显示调试循环／游戏单次规则，保留高级速度与 Root 参数。

## 3. 动作引用和默认值多处推导

- 招式既保存 actionName 又保存 actionFile：`src/combat-move-manager.js:132`；动作配置用名称作键，动作新增的文件映射在 `src/motion-editor.js:671` 写入内存 ASSETS。
- 动作编辑器通过 `src/motion-editor.js:1935` 重建映射，支持后缀匹配；共享招式助手 `src/combat-move-manager.js:320` 附近使用规范名匹配与文件推断，策略不完全相同。
- 动作保存 `src/motion-editor.js:1214` 只提交 motionConfig，任意自定义别名与文件的关联存在重载后无法恢复的风险。
- 默认值见 `src/motion-editor.js:37,1894,1909`，游戏另有 `src/main.js:238` 启动回退。
- 建议统一持久化的资源引用与默认解析，显式保留历史别名；不要取消自由命名，也不要静默改名。

## 4. 方向归属与检索重复

- 方向定义存在于 `src/combat-move-manager.js:1` 和 `src/combat-controls.js:3`，方向池又保存 key、id 和 moves；每招另有 triggerDirection（`:108,132`）。
- 修改归属要先更新 triggerDirection，再从所有列表删除并插入新池：`src/move-manager.js:217`。
- `src/combat-move-manager.js:246,255` 每次查询重新归一化和展开列表；游戏 `src/main.js:1536,1548` 重复经过这些入口。
- 建议近期统一方向定义、校验归属，加载后索引；未来出现跨方向复用时，改为单独的招式定义与方向池引用。
- 不能删除方向池自己的权重与缺省项，也不能让角色特长改写玩家指定的方向。

## 5. 保存和引用校验薄弱

- 编辑器分别保存整份文档：`src/motion-editor.js:1214`、`src/move-manager.js:232`、`src/model-editor.js:1500`。
- API 只检查顶层对象：`vite.config.js:61,99,138`，未检查跨文件动作／碰撞体引用、区间上界和缺省 ID，也未检查旧版本覆盖。
- 特别要修正：`saveMotionConfig` 在 `src/motion-editor.js:1214` 捕获错误但不抛出或返回失败；新增 `:671` 和删除 `:710` 随后仍可显示成功。这不是需要更多配置项的问题，而是错误传播应有一个清晰约定。
- 建议共享校验和保存结果协议，增加必要的版本冲突提示；不需要引入数据库或跨文件事务框架。

## 6. 预览状态绑定与维护成本

- 招式预览 `src/move-manager.js:125` 切换模型时只更换 activeCharacter，`:245` 却采样新角色 mixer，`:126` 才创建对应 action。对照动作编辑器 `src/motion-editor.js:463` 的模型切换后重建动作，存在状态不一致风险。
- 招式时间轴选择 `src/move-manager.js:205` 仅 renderAll；拖拽 `:208` 和显式窗口选择 `:213` 会重建碰撞体。更新路径应集中为一个“选择／预览刷新”入口。
- `src/main.js:2696` 的 updatePlayer 在 return 后保留整段旧移动实现，而现有共享移动函数在 `:2821`，应删除不可达副本。
- 玩家更新 `src/main.js:1944` 与 NPC 更新 `:3363` 的生命周期可提取共同行为；AI 冷却、玩家缓存和目标来源是合理差异，应保留在适配层。
- 当前测试 `tools/test_combat_controls.mjs:89` 依赖 AST 提取私有函数；抽出少量共享模块后可直接导入测试，降低改文件结构时的维护成本。

## 处置顺序

1. 预览处理一致性、保存失败正确反馈、模型切换状态。
2. 有效配置与引用校验、联动时间轴和基础／高级分层。
3. 招式定义与池引用迁移、运行时索引及模块拆分。

第三项在招式数量较少时属于长期维护优化，不是已证明的性能问题。
